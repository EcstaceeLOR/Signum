## Network availability for Chain Jam

Chain Jam's published entrant workflow uses the local simulator; it does not
publish a shared public testnet, faucet, RPC endpoint, or permissionless
production registration path. The simulator provides a local chain, a real
local Verify Network VRF node, a casino host, and 1,000,000 test chUSD. It is
the supported environment for end-to-end wagering before Chain performs a
production integration.

The hosted standalone URL therefore runs a no-funds Practice mode. It becomes
real Chain play only when embedded by an authorized Chain host with a deployed
and registered game contract. Never present local test chUSD or a simulator
address as a public testnet or production deployment.

## Why the SDK is vendored

The [official Chain Jam setup](https://jam.chain.wtf/#build) names `@chain/casino-sdk`, but that package is not available from the public npm registry. Chain distributes the bridge sources through its shadcn registry and distributes the complete simulator, VRF node, canonical interface, and coinflip example as an unversioned ZIP.

Signum vendors the complete official ZIP at [`vendor/chain-casino-sdk`](../vendor/chain-casino-sdk) so that:

- a clean checkout does not depend on the unversioned archive remaining unchanged;
- the exact bridge and canonical `ICasinoGameV2` interface can be reviewed with the game;
- the official coinflip baseline remains available before the Signum contract exists;
- simulator dependencies can be locked independently from the Signum application.

The imported tree differs from the archive only in these reproducibility and runtime-hygiene adjustments:

- `package-lock.json` is generated by Signum to pin the workspace dependencies.
- `simulator/package.json` pins Hardhat to `3.12.0` instead of the upstream `^3.12.0` range. The range currently resolves to Hardhat 3.17, whose modularized CLI no longer provides the `builtin:node` plugin expected by this SDK release. The exact upstream minimum retains the SDK's bundled `hardhat node` workflow.
- `simulator/src/ChainSmallLogo.tsx` uses React's camel-cased SVG property names so the official simulator runs without React console errors.
- `.gitignore` stops excluding the bundled `local-verify-network`, `slot-engine`, and lockfile so a clean Signum checkout contains the complete official workspace.
- `docs/VISUAL_AND_UX.md` removes three trailing spaces that fail `git diff --check`; its content is unchanged.
- `local-verify-network/src/local-verify-network.ts` accepts optional fulfillment-delay environment variables used only by Signum's cancellation E2E path; default simulator behavior is unchanged.

## Runtime version

The current SDK package metadata declares:

```json
{
  "engines": {
    "bun": ">=1.4.0",
    "node": ">=24.12.4"
  }
}
```

Some upstream prose still says Node 22+. The executable `package.json` constraint is treated as authoritative, so Signum uses Node **24.12.4 or newer**. Node never published a 24.12.4 release (the release line moves from 24.12.0 to 24.13.0), so `.nvmrc` pins the available Node **24.21.0 LTS**. This satisfies the SDK's declared floor and the issue's Node 22+ requirement.

Use the repository `.nvmrc`:

```sh
nvm use
node --version
```

## Clean-checkout coinflip workflow

From the Signum repository root:

```sh
npm ci
npm run simulator
```

`npm run simulator` performs a clean install from the vendored SDK lockfile and then runs the upstream `npm start` command. It starts:

- the in-memory Hardhat chain and local Verify Network VRF node;
- the minimal casino host and test chUSD deployment;
- the simulator harness at <http://localhost:3300>;
- the official coinflip guest at <http://localhost:3100>.

Open <http://localhost:3300>. The setup panel should discover the local deployment automatically and mount the coinflip example. The default player begins with 1,000,000 test chUSD.

For subsequent starts that do not need a clean dependency reinstall:

```sh
npm run simulator:start
```

To verify the vendored workspaces without keeping servers running:

```sh
npm run simulator:check
```

That command production-builds the simulator and the official coinflip guest. The upstream ZIP's workspace-wide `check-types` command is not used as a Signum gate in this pinned release: simulator and coinflip tests import `vite-plus/test`, but the archive does not declare `vite-plus`, and the optional slot-engine test suite currently contains unrelated `unknown` type errors under its resolved dependency tree. Signum does not patch those upstream sources or depend on the optional slot engine. Runtime startup and the two required production builds are the Issue #3 acceptance boundary.

## Automated Signum lifecycle

From a clean checkout, install both dependency trees and Chromium once, then run the full lifecycle:

```sh
npm ci
npm run simulator:install
npm run playwright:install
npm run test:e2e:simulator
```

The E2E runner stages the canonical `contracts/SignumGame.sol` and `contracts/SignumGameData.sol` into the simulator's watched contract folder for the duration of the run. It then starts the in-memory Hardhat chain, real local Verify Network node, casino host, simulator UI, and Signum Vite guest. The browser test:

1. opens a session through the iframe bridge and observes `WAITING_RANDOMNESS`;
2. waits for real VRF settlement and checks the rendered match count, multiplier, and payout agree;
3. opens a second session with fulfillment intentionally delayed, mines past its randomness deadline, and cancels it through the guest UI;
4. fails on browser exceptions, console errors, local request failures, bridge regressions, or lifecycle timeouts.

Stack logs, Playwright traces, screenshots, and videos are written under `test-results/` and uploaded by CI on failure. The runner always stops its exact child processes and removes only the two contract copies it staged.

## Signum contract drop-in path

The simulator watches:

```text
vendor/chain-casino-sdk/simulator/contracts/
```

When the Signum contract is implemented, place its simulator copy at:

```text
vendor/chain-casino-sdk/simulator/contracts/SignumGame.sol
```

It must import the canonical interface as:

```solidity
import {ICasinoGameV2} from "./ICasinoGameV2.sol";
```

The local node compiles and auto-deploys every constructor-free contract in that folder that implements `ICasinoGameV2`. It then registers the deployment and adds it to the game picker without restarting the stack. Contracts with constructor arguments must be deployed manually against `http://127.0.0.1:8545` and entered in the setup panel.

The production contract should ultimately have one canonical source under Signum's own `contracts/` directory. Until a contract-sync step is added, changes to the canonical source and simulator copy must be kept byte-for-byte aligned and checked in the contract issue.

## Frontend workflow

Signum's Vite server remains independent from the vendored coinflip guest:

```sh
npm run dev
```

Point the simulator at it with:

```text
http://localhost:3300/?game=http://localhost:5173&gameAddress=0x…
```

The frontend resolves `@chain/casino-sdk/guest` directly to the pinned vendored source through matching TypeScript and Vite aliases. The root application pins Penpal `7.0.6`, the exact bridge transport resolved by this SDK release, so clean root installs can bundle the official guest implementation without publishing the private workspace package.

`src/bridge/chainHost.ts` owns the single host connection, stores pushed snapshots, and exposes only typed host methods. `src/bridge/useChainHost.ts` shares that connection across React StrictMode remounts and destroys it after the final consumer unmounts. Signum never requests a wallet provider or signs raw transactions: wallet readiness, balances, sessions, and all signing operations remain host-owned.

## Current integration assumptions

- The SDK is a private npm workspace package, not a public registry dependency.
- `ICasinoGameV2.sol` in the vendored simulator is the canonical interface for this pinned release.
- Game step handlers are `view` and are reached through static calls.
- The simulator uses real local ECVRF proofs rather than mocked random values.
- The harness intentionally models optimistic sessions, flashblock updates, lagged indexing, guarded balances, and stuck-randomness cancellation.
- The host owns wallet and signing behavior; the guest iframe contains no wallet integration.
- The bundled coinflip contract and guest are the integration baseline, not Signum code.
- A future SDK update is deliberate work, not an automatic dependency bump.

## Updating the SDK

1. Download the current official archive to a temporary directory.
2. Record its SHA-256 and inspect its root `package.json`, changelog, canonical interface, and contract constraints.
3. Compare the new archive with `vendor/chain-casino-sdk` before replacing anything.
4. Replace the vendored workspace, regenerate its `package-lock.json`, and update this document.
5. Run `npm run simulator:check` and the full `npm run simulator` coinflip flow.
6. Re-run Signum contract, bridge, lifecycle, and golden-vector tests once those exist.

Do not update only the bridge files or only the Solidity interface. The simulator, host behavior, guest types, and interface form one compatibility unit.
